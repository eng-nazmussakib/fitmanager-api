# fitmanager-api

The FitManager API: Express 5 and TypeScript, run natively by Node 26, with raw SQL on PostgreSQL 18 (D-028, D-047). It is a hobby project that only ever runs as a **free demo (D-075)**: on Cloudflare Workers (Free plan) through Hyperdrive to Neon, with member photos and documents in R2. It talks to no other outside service: no mail, SMS, payment gateway, captcha, identity provider or error tracker. There are no scheduled jobs: a time-based rule runs when its data is read.

```bash
nvm use            # Node 26 (>= 24.12 works)
npm ci
# The schema and demo data come from fitmanager-infra/db (D-039); this API never migrates or seeds.
(cd ../fitmanager-infra/db && npm ci && PGLITE_DIR=../../fitmanager-api/storage/pglite npm run seed)
npm run dev        # http://localhost:3000/api — no database server needed (PGlite)
```

With `.env.local` pointing at a PostgreSQL server instead, run `DATABASE_URL=… npm run seed` in `../fitmanager-infra/db`. After a new migration lands there, run `npm run migrate` there again (stop the API first when it uses PGlite).

Sign in with the demo staff accounts (`fitmanager-infra/db/seeds/demo/001_branches_and_staff.sql`): `owner` / `Owner@123` (every branch through HQ), `manager.gulshan` / `Manager@123`, `desk.gulshan` / `Desk@123`, `desk.uttara` / `Desk@123` (front desk at two branches) and the rest of the list on the web app's `/demo` page. Rules apply per branch: send `X-Branch-Id` with a branch id from `/v1/auth/me`. Try the requests in [requests.http](requests.http) (VS Code REST Client), or point the web app at it:

```bash
cd ../fitmanager-web && API_TARGET=http://localhost:3000 npm run start:proxy   # http://localhost:4200
```

## Scripts

| Command                        | What it does                                                                                             |
| ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `npm run dev`                  | API with auto-restart (`node --watch`), PGlite in `storage/pglite`, pretty logs                          |
| `npm test` / `npm run test:ci` | Vitest (watch) / one run with coverage                                                                   |
| `npm run test:pg`              | One run on a real PostgreSQL: `TEST_DATABASE_URL` from `.env.local`, a throwaway database per test file  |
| `npm run typecheck`            | `tsc --noEmit`                                                                                           |
| `npm run lint` / `format`      | ESLint 10 (type-checked) / Prettier                                                                      |
| `npm run validate`             | format check + typecheck + lint + tests: run it before pushing (the commit hook only lints staged files) |
| `npm run worker:db`            | Serves `storage/pglite-worker` over TCP on 5433 for `worker:dev` (seed it first, see `wrangler.jsonc`)   |
| `npm run worker:dev`           | The API as a Cloudflare Worker in local workerd, http://localhost:8787 (needs `.dev.vars`)               |
| `npm run worker:check`         | Bundles the Worker and profiles its start-up (`storage/startup.cpuprofile`)                              |

There is **no build step**: Node runs the `.ts` files itself (type stripping, stable since Node 24.12). `tsc` only type-checks. The code is therefore limited to syntax that can be erased (no `enum`, no `namespace`, no constructor parameter properties), and `erasableSyntaxOnly` enforces that. Imports use `.ts` extensions and the `#src/*` subpath alias from `package.json`, which Node, TypeScript and Vitest all understand without extra config.

## Layout

```
../fitmanager-infra/db/            migrations, demo seeds and their runner (D-039): the schema is not this repo's job
src/
  server.ts            Node entry for local development: config → logger → deps → listen
  worker.ts            Cloudflare Workers entry (the hosted demo): the same createApp(deps), a pool per request
  worker/              the RateLimitCounter Durable Object
  app.ts               createApp(deps): middleware order, routers, 404, error handler (no listening, no globals)
  container.ts         AppDeps: db, cache, clock, files, tokens, rate-limit stores, created once, injectable
  config/env.ts        every env var, validated with Valibot
  db/                  Db interface (pg | PGlite), sql`` tagged template, withBranchTx (tenancy, RLS context)
  auth/                CASL abilities, scrypt passwords, jose tokens, refresh rotation, authenticate/requireAbility
  lib/                 http envelope + parse(), errors, logger, memory cache, rate limits, clock, file stores (R2, disk)
  features/<name>/     one router per feature (+ service, repo, schema, tests): auth, branches, plans, members, sales, …
  testing/             createTestApp() on a fresh PGlite (or a real server), signIn() helper
```

To add a feature, copy `features/plans`: a Valibot schema, a repository with SQL, a service, a router with `authenticate` + `requireBranch` + `requireAbility(...)`, and a test file. Mount it in `app.ts`. Add the subject to `auth/ability.ts` **and** the web app's `ability.ts`. If the feature would need an outside service, build a manual stand-in instead (D-075); if it is time-based, run it when its data is read, never on a schedule.

## Configuration

All variables are in [.env.example](.env.example) and validated in [src/config/env.ts](src/config/env.ts); the app refuses to start with any invalid one and lists them all. `NODE_ENV` defaults to `production`, which also refuses PGlite and the development JWT secret. Locally they come from `.env.development` and the git-ignored `.env.local`; on Cloudflare from `wrangler.jsonc` vars and Worker secrets (`JWT_SECRET`, the `S3_*` keys for R2; `../fitmanager-infra/cloudflare/demo-deploy.md`).

## Auth design

- **Access token:** a JWT (HS256), 15 minutes, with `sub` = user id and `sid` = the session (refresh-token family) only (roles are per branch, so they are not in the token); `iss` and `aud` are checked. Each request verifies it in memory and reads the user's profile and rules from the cache (30 s), not from the database every time.
- **Refresh token:** opaque, 7 days, stored as SHA-256. Each refresh issues a new one and retires the old one. Replaying a retired token revokes the whole sign-in "family". Within `REFRESH_REUSE_GRACE` (30 s) a replay is treated as two tabs refreshing at once and gets a new token. A user's tokens that expired or were revoked over a day ago are deleted at their next sign-in (no clean-up job, D-075).
- **Temporary passwords (D-054, D-064):** staff added by an admin, or reset by one, and members given portal access at the desk get the password typed for them and `must_change_password`. Until they set their own, every route except `/auth/me`, `/auth/change-password` and `/auth/logout` answers 403 with `errors[0].path = "PASSWORD_CHANGE_REQUIRED"`. This is the manual stand-in for an email reset (D-075).
- **Authorization (D-034):** CASL rules per role (`app_role.rules`, JSON, versioned in migration 002). A user holds one role per branch (`staff_assignment`); `all_branches` users (the owner) reach every branch with their HQ role. The ability for a request is the global rules (by user kind) plus the rules of the assignment at `X-Branch-Id`, built in `authenticate`. Branch routes add `requireBranch('BRANCH' | 'HQ')` (403 for a branch the user does not work at) before `requireAbility(action, subject)`. Actions and subjects are typed, so a typo is a compile error. `/me` sends the same rules to the web app.
- **Passwords:** scrypt, `scrypt$N$r$p$salt$hash`. The cost of new hashes is `PASSWORD_SCRYPT_N`, `_R`, `_P`. The default (1024, 8, 1: about 2 ms of CPU) is cheap on purpose, for the 10 ms CPU limit of Cloudflare Workers on the Free plan (D-032); it is below OWASP's minimum, which is acceptable for demo data. Hashes made with other settings still verify and are re-hashed at the next sign-in.
- **Login:** limited per IP + username (a Durable Object per key on Workers), one message for unknown user and wrong password. Wrong credentials answer **400**, not 401, because the web app treats 401 as "session expired" and would not show the message.

## Database

- **Drivers:** `DB_DRIVER=pg` (node-postgres pool, statement timeout, `application_name`) for a real server; `pglite` (PostgreSQL 17 in WebAssembly) for `npm run dev` and the tests. Repositories only see `Queryable`.
- **SQL:** ``sql`… ${value} …` `` produces `$n` parameters. Fragments compose (`sql.where([...])`, `sql.join`). `sql.raw` is only for whitelisted identifiers. `containsPattern()` escapes LIKE wildcards.
- **Pitfalls handled:** `date` is selected `::text` (node-postgres otherwise makes a JS Date at local midnight, which shifts a day across time zones), `numeric` is `::float8`, counts are `::int` (pg returns bigint as a string), and unique/foreign-key violations map to 409/400.
- **Migrations and seeds are not the API's job (D-039):** `fitmanager-infra/db` holds `migrations/`, `seeds/` and the runner that applies them (`npm run migrate | seed | status | reset` there), run from a laptop. The tests build each throwaway database with the same runner (`src/testing/test-app.ts` imports `../fitmanager-infra/db/tools/runner.ts`), so the infra repo must sit next to this one.
- **Transactions:** `db.transaction(async tx => …)` rolls back on throw. When a change must survive a failure (a revoked session), the transaction **returns** an outcome and the error is thrown after the commit.
- **Time-based rules without jobs (D-075):** `closeFinishedVisits` (attendance: visits still open after the branch closed are closed at the closing time when the branch's floor is read), `writeDueReminders` (notifications: expiry reminders 7 days and 1 day before a plan ends, written when a member's messages are read, dated their due day), `refreshTokens.prune` (at sign-in). Each is idempotent and safe under concurrent requests.

## Testing

`npm test` runs the real app (`createApp`) on a fresh in-memory PGlite per test file, with an in-memory cache and file store, through supertest. There are no mocks of `pg`, and the SQL, constraints and migrations are the real ones. `db.test.ts` covers the `pg` driver itself over a real wire connection, using PGlite behind its socket server. `npm run test:pg` runs the same suite on a real PostgreSQL server instead: each test file creates its own `fm_test_<random>` database from `TEST_DATABASE_URL` (the role needs CREATEDB), migrates and seeds it with the infra runner, and drops it at the end. On this project's machine that is the local PostgreSQL 17 (`.env.local`).

## Deployment

The hosted demo is the only deployment (D-075): `src/worker.ts` on Cloudflare Workers runs the same `createApp(deps)` through `handleAsNodeRequest` (`cloudflare:node`), with a database pool per request through Hyperdrive (no I/O may outlive its request on Workers), the app built at start-up (global scope), rate limits counted in a Durable Object (`src/worker/rate-limit-counter.ts`) and files in R2 over its S3 API. Cloudflare's Git integration deploys it on push (D-046). The steps, secrets and checks are in `../fitmanager-infra/cloudflare/demo-deploy.md`. Logs go to Workers Logs (free); filter by `reqId`.

## Known limitations

- **Caches are per isolate:** the user cache (30 s) and public caches live in each Worker isolate's memory, so a role change can take up to 30 s to reach every isolate.
- **Large exports:** they load up to 50 000 rows into memory.
- **Dev-only audit warnings:** `npm audit` reports `minimatch` inside ESLint 10's own dependencies (dev only; it never handles untrusted input).
